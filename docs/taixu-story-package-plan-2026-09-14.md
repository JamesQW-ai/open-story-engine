## 目标与本轮交付边界

基于《太虚遗录》第一部现有十万字母本，规划一个能够支撑长篇互动的版本化 StoryPackage。核心目标是保持人物、世界规则、物品、知识边界和跨卷因果的一致性，同时允许玩家行动形成有代价、可追溯的私有分支。

本轮交付本规划文件，以及为规划进行的只读核查结论。尚未冻结发布母本、修改小说或代码、生成可执行故事包、创建试玩会话，也未进行真实模型验收。下文的新字段、目录和门槛均为待实施设计，不代表现有引擎已经支持。

建议采用“全书证据与骨架先行 → 第一卷可玩切片 → 逐卷扩展 → 全书验收”的顺序。首卷通过不能替代十万字全书通过；全书有结构索引也不能替代可玩性验收。

## 规划依据与待统一口径

### Gemini 参考的采用方式

参考用户提供的 [互动式同人小说项目构想 — Google Gemini](https://gemini.google.com/app/4dce0b1306db6fce)。2026-09-14 浏览器读取两次因 `Codex auth token is unavailable` 失败；随后用户在本任务粘贴了最新结论。本文使用该粘贴内容，不声称读过整段在线对话。

采用其五个重点：全局主线与卷级推进、动态角色与关系、世界硬规则与信息差、物品与场景、上下文与负向约束。工程上采用全局精简信息加当前剧情切片。

结合本仓库作三项具体化：

1. 官方包保存原著事实、规范变化与规则；实时状态保存在各会话分支中，不在官方包内维护一个所有玩家共享的 `state-ledger.json`。
2. 全书结局、伏笔答案可供后台规则校验；正文模型每轮只获得已解锁的目标与事实。“每轮必带全局配置”不等于每轮注入终局秘密。
3. 因果锁约束已发生选择的后果，不强迫玩家完成原著中的未来选择。原著路线是规范参考，分支不得无理由回归它。

### 产品入口存在的文档冲突

本任务提供的 `AGENTS.md` 仍指定方向 2 为 MVP；工作区中的 [产品计划](product-plan-2026-09-11.md)、[产品方向](product-direction.md) 和 [验收标准](mvp-acceptance.md) 已写入“官方小说、未知读者开局”的新定位，部分历史条款仍混在正文中。

本规划不据此静默修改产品入口。先定义两种入口都需要的长篇内容底座；遵循本任务显式规则，首批验收保留方向 2 的节点与角色介入。开篇同时作为内容质量基线。是否将正式入口统一为未知读者开局，列为后续产品规则统一事项，不阻断母本索引与语义审校。

### 已知内容风险

收口记录明确保留第 41–44 章的天庭追杀、陆无回等旧线问题；本轮定点检索仍能看到相关内容。其与北河城、三方公议及人间留白收束的因果兼容性需专项审校，不能由抽取器自行合并或删去角色解决。

第一部可进入离线解析与候选骨架整理；全书发布须先关闭影响终局的连续性冲突。第 45–50 章的局部收口不自动使第 41–44 章通过。首卷若引用末卷真相作为后台规则，相关未决真相也必须隔离，不能进入首卷权威配置。

### 现有抽取器的实测缺口

本轮在内存中运行 `analyze_standard_novel`，没有写出分析文件或调用模型：

| 检查 | 结果与影响 |
| --- | --- |
| 总体输出 | `status=candidate`，覆盖 50 章；共 122 条事件候选，不能视为 122 个已审核 Beat |
| 人物名 | 16 个不同候选名中出现“陆照”“顾长”“权限”“路边”等误识别；未得到完整的陆照临、顾长离、沈砚秋、叶观澜、陆沉舟 |
| 关键实体 | 玄霄宗、残印、无相镜未成为对应实体候选；青痕也需明确归入身体标记或状态，而非默认当作便携道具 |
| 章节事件 | 第 8 章事件候选为 0；当前 `_assert_semantic_completeness` 要求每章有事件，因此未经补充审核的结果不能直接完成构建 |
| 世界事实 | 当前事实规则包含交通、通信等词型；50 条事实候选并不证明已覆盖修炼与记忆代价规则 |
| 卷级结构 | `_compile_arc_model` 按章节分组生成 Arc，不能直接视为五卷长篇的语义阶段图 |

因此，现有命令链可复用，但不能把本书直接导入后的结构产物作为已完成的故事包。优先建立本书专属的、带正文证据的审核标注输入；通用构建器负责稳定 ID、结构编译和校验，避免把本书人名与规则硬编码进运行时。

## 二、五模块内容契约

### 1. 全局主线与卷级图谱

使用 `Book → Act（卷）→ Arc（因果阶段）→ Beat（可审阅拍点）→ Turn（玩家回合）`。Gemini 中的“大卷 Arc”在本仓库规划中映射为 Act，以免与现有章节 Arc 混淆。章节是原文索引维度；一个 Arc 可以跨章，一个章节也可以包含多个 Beat。

以下只是依据现有十万字大纲的初始分组，必须逐章对照正文确认：

| Act | 来源章节 | 审核重点 |
| --- | --- | --- |
| 山门雨夜 | 1–10 | 父亲失踪、封山、废井与残印，主角离宗前后的选择与证据 |
| 旧墟寻灯 | 11–20 | 无灯镇、顾氏旧史、引灯人与记忆差异 |
| 金丹之誓 | 21–30 | 三方条件、修炼代价、证词、盟约与背叛 |
| 归墟天门 | 31–40 | 名字消失、权力冲突、开门条件与不可逆代价 |
| 人间留白 | 41–50 | 灾后救人、三方结果、终局选择及未解事项的交接；先处理旧线冲突 |

每个 Act/Arc 记录目标、起因、冲突、转折、完成条件、输入状态、结果状态和未解事项。每个 Beat 记录 `sourceRefs`、场景、参与角色、前置条件、规范结果、可改写范围、条件后继以及线程变化。Beat 数量由事件审校决定，不按段落数或固定回合数机械生成。

将原著已发生事件、未来规范事件、分支新增事件分开。进入第 N 个拍点时，只继承入口前已确认历史；入口后的规范结果保持未发生。因果边包含触发条件、后果、期限和替代解决条件，例如某次已接受的帮助带来后来需要兑现的承诺；玩家改变前置选择后，不得继续无条件套用原著后果。

伏笔与开放线程必须有来源、知情范围、建立拍点、预期处理阶段、优先级、关闭条件和关闭证据。状态区分未揭晓、已揭晓未解决、已解决、因分支失效、明确延期。结局检查逐项验证关键线程，不能仅靠一个“回收率”掩盖未完成的核心危机。

### 2. 动态角色卡与关系矩阵

官方角色卡保存：真实姓名与别名、身份阶段、来源段落、核心动机、不可轻易跨越的底线、说话方式、行为习惯、能力边界，以及原著中各阶段的变化。

人物声音从实际台词抽取，附代表性段落。没有稳定证据的口头禅或禁词标为 `Unknown`；不为每个人发明标签，也不靠统一的“冷淡短句”制造同质化。

分支中的身体状态、修炼阶段、动机变化、关系、位置、持有物和知识单独记录。关系有方向、有事件证据；“帮助过”不自动等于“完全信任”，心理变化也不能仅根据人物共同出场推断。

初批重点核对陆照临、顾长离、沈砚秋、叶观澜、陆沉舟；同时建立全书角色目录。对萧问蝉、陆无回等待审旧线角色保留原文记录和冲突状态，不能从权威角色卡中静默消失。玩家代入原著角色后，该角色不应又以独立 NPC 身份重复行动。

### 3. 世界观硬规则与知识边界

分清三类内容：世界客观规则、特定时间已发生的事实、角色陈述或猜测。宗门宣告、证词、幻象和传闻都可能不可靠，不得自动编译为世界铁律。

优先审校修炼阶段、太虚力量的触发与记忆代价、残印能力、封山与通行条件、势力权限和名字/记忆变化机制。数值或绝对禁令须有正文证据或明确的互动设计批准；没有证据时不得把“大纲倾向”升级为铁律。

知识记录至少包含事实 ID、知情角色、获得方式、获得事件及有效阶段。把读者知道、玩家知道、当前角色知道分开；记忆被夺走时，还要记录该角色失去哪项认知、是否仍有外部记录、能否经后续事件重新获知。世界历史仍可成立，但角色不一定记得。

硬规则由本地校验执行，正文模型只能提议。将后来才揭示的秘密作为后台约束时，只向模型提供本轮必要的可表达边界，不能在负向提示中直接写出秘密答案。

### 4. 关键道具与场景记忆库

实体注册应区分物品、身体标记、能力、文书记录与场景装置。残印的载体、掌心印记和可移动石片是否为同一实体或不同阶段，要根据原文逐次变化确认；不能因名字相近直接合并。

物品至少记录稳定 ID、别名、首次出现、载体、可携带性、所有者与实际持有者、所在地点、损坏/耗尽/封存状态、允许的变化及证据。每次转交、使用和损坏通过事件更新；同一物品不得同时由两人独占持有。

地点记录空间层级、已知出口、相邻地点、通行条件、视线/听觉范围及场景装置。只有正文直接支持的连接才能进入权威拓扑。同章出现两个地名不代表存在直达通道；正文未说出口数量时，不能将“发现两个出口”写成“只有两个出口”。

首批检查玄霄宗山门、废井、西坡、北河城、无灯镇等地点，以及引路灯、灰白石片/残印、旧档、无相镜等实体。具体别名、类型与关系以标注审校为准。

### 5. 文风、负向约束与上下文装配

母本采用的叙述方式和互动玩家视角要分别声明。首批互动正文建议使用第二人称限知；若后续入口采用其他视角，需在会话契约中明确，不能逐回合漂移。母本文字不因转换互动视角而被修改。

文风以实际母本为样本，重点保留场景细节、行动因果、人物辨识度和选择代价。约束包括：不替玩家完成未选择的关键决定、不泄露未解锁伏笔、不补出可跨回合使用的未登记物品或通道、不靠总结性套话代替事件推进、不靠同句复读凑篇幅。

运行时只装配：极简规则与风格、当前 Arc 目标和当前 Beat、相关角色的可见资料、当前场景与必要物品、当前分支有效状态、有限历史摘要与到期线程。历史摘要不是权威状态；发现摘要与事件状态冲突时，以已确认事件和状态为准。

预算建议：每轮固定规则与风格小于 1,000 tokens；其余上下文设置独立总预算，按实际模型 tokenizer 测量后确定，不能用汉字数冒充 token 数。超预算优先减少无关背景和历史复述；不得截断当前硬规则或必要事实。若最小有效上下文仍超预算，应返回明确的受控失败。

## 三、静态包、审核输入与运行期的存储边界

优先扩展现有 `package.json` 与 `modules/` 体系，不建立另一套与 `runtime-index.json` 竞争的加载入口。Gemini 的 `master-config.json` 对应本设计的精简运行时投影，其权威来源仍是已审核包中的规则模块。

以下为目标逻辑布局；新模块文件名与 schema 需在实施阶段冻结，不能直接交给当前加载器：

```text
content/authoring/taixu-relics-part1/<source-revision>/   # 拟新增：离线内容工程
  source-freeze.json                                  # 源哈希、分章哈希、口径、版本
  source-manifest.json                                # 已有 manifest 契约
  analysis.candidate.json                             # 原始候选，保留误识别证据
  analysis.reviewed.json                              # 经审核的编译输入
  review-decisions.json                               # 审核人与逐项接受/拒绝/待审记录
  continuity-issues.md                                # 冲突与关闭证据
  coverage-matrix.md                                  # 全书章节与五模块覆盖

content/packages/taixu-relics-part1/<version>/          # 审计通过后才安装
  package.json / analysis.json / audit.json / reader.json
  modules/
    package-index.json / runtime-index.json
    main-story-graph.json / world.json / state-schema.json
    characters/ / relationships/ / locations/ / items/
    chapters/ / arcs/ / beats/ / entries/ / reader/
    acts/ / threads/ / style.json                      # 拟扩展，需 schema 与加载器支持

隔离 SQLite / 会话存储                                 # 使用现有持久化体系
  SessionStoryContract + BranchState + branchLedger
  game_events / 各分支历史 / 模型审计
```

包中的动态描述表示“原著各阶段的规范变化规则”，不是玩家当前状态。每个成功提交的回合就应持久化状态；到 Beat 边界可额外生成快照，不能等整拍结束才保存中途交物或受伤。失败草稿、未选择方向和图片任务均不推进权威事实。

各来源标注区分 `source_fact`、`reviewed_interaction_rule`、`branch_event`。人工设计的偏离规则可以进入已批准的互动层，但不能伪装成原著原句。最终可执行 JSON、引用、状态条件和哈希仍由 Python 生成与审计。

## 四、实施阶段与可验收交付物

| 阶段 | 工作与交付物 | 退出条件 |
| --- | --- | --- |
| P0 母本候选冻结与风险登记 | 保存字节快照、50 章清单、哈希、计数口径；登记旧线冲突与产品入口冲突 | 输入唯一、哈希可复验；候选冻结不冒充发布冻结 |
| P1 全书实体与事实审校 | 逐章审核人物、地点、物品、关系、事件、知识、修炼与记忆代价；产出 reviewed analysis、review decisions、coverage matrix | 50 章均有审校记录；无误截人名；每章至少一个真实事件；关键实体与规则均有证据或明确未决状态 |
| P2 五模块与编译契约 | 整理五卷及跨章 Arc；标注条件边、伏笔、终局与人物知识变化；定义审核门槛和新增模块加载方式 | 源事实与互动规则分离；未知内容不能进入可执行条件；旧 schema 有明确兼容边界 |
| P3 第一卷可玩切片 | 以第 1–10 章约两万汉字为范围；优先跑通开篇、残印事件和离宗阶段，再扩至整卷 | 规范推进、自由改写、知识隔离、物品变化和至少一个 Arc 的阶段结果均可验证 |
| P4 逐卷扩展与跨卷回归 | 依次开放第 11–20、21–30、31–40、41–50 章；每卷附角色/规则/线程差异与转场测试 | 各卷入口承接前卷结果；跨卷代价不消失；第 41–44 章问题已关闭或有明确的已审修订版本 |
| P5 全书候选发布验收 | 根包与模块审计、隔离 mock、真实模型抽样、人工试玩、全书线程与终局检查 | 可区分内容完成、结构通过、离线可玩和正文质量；没有未关闭的发布阻塞项 |

依赖顺序为 P0 → P1 → P2 → P3 → P4 → P5。P1 可保留待审事项以供 P2 整理候选图，但 P3 中所有被引用的内容必须审核通过。末卷问题若影响首卷初始规则，也会阻断相应首卷功能。

### 首卷切片的兼容策略

当前构建器要求分析按序覆盖全部源章节。因此不能把十章分析直接传给五十章母本，也不能把第十章误标为全书结局。

优先方案是全书建立完整候选索引，发布层仅开放已审核的首卷范围；这要求增加明确的内容可用范围与阶段完成状态。若当前加载器不能支持，先生成独立、可追溯的首卷派生输入并使用独立包 ID；其清单必须记录完整母本哈希和原文范围，结尾只能表示“切片完成”。实施时选择一种方案并写入验收证据，不能静默截断全书。

### 后续可能涉及的代码责任

- `open_story_engine/source.py`：复用源索引；仅在验证发现解析缺陷时修改。
- `open_story_engine/package_builder.py`：优先补充审核输入、语义完整性门槛、稳定实体合并与长篇图编译；本书专属标注放在内容层。
- `open_story_engine/content.py` 及实际上下文解析模块：新增模块审计、按需加载、可见性和上下文预算；先核实既有能力再决定改动。
- 状态与生成模块：仅为已冻结契约补充当前缺失能力。工作区已有 `cocreation.py` 等未提交改动，实施前重新核对责任范围。
- 本阶段规划不包含前端重建、入口删除、自动配图或多书库建设；图片只预留场景引用，不作为首个内容包通过条件。

## 五、验收矩阵

| 验收面 | 必须覆盖的证据 | 通过线 |
| --- | --- | --- |
| 源版本 | 合订本、分章索引、输入哈希、包源引用 | 编译输入与审核记录属于同一版本，引用范围均可回查 |
| 语义覆盖 | 50 章 × 五模块覆盖矩阵；无相关内容时说明理由 | 无伪造实体；关键因果、人物、物品与规则没有无说明缺口 |
| 角色声音与动机 | 主要角色的原文台词依据、不同阶段行为及负面样例 | 不把未选择行为或统一人格强加给角色；改变有事件依据 |
| 知识与记忆 | 两名角色不同知情范围；失忆、获知、再获知过程 | 未到揭示点的真相不进入正文上下文；世界事实与角色记忆不混淆 |
| 道具与拓扑 | 取得、交付、使用、损坏、跨场景携带；非法通行 | 所有权/持有权和位置一致；禁止凭空增加可用通道与道具 |
| 主线与偏离 | 规范路径、兼容偏离、严重偏离后至少三个连续回合 | 已选行为有后果；未选未来事件不被当作历史；不强拉回原线 |
| 长期因果 | 早卷建立、后卷兑现的承诺/代价/伏笔；跨卷回放 | 不因换卷清空状态；关闭线程有实际事件，不能只改摘要 |
| 收束 | 一个完整 Arc、首卷阶段结束、全书终局条件 | 满足条件才结束；切片末尾不冒充全书结局；关键冲突逐项处理 |
| 状态与失败 | 两分支隔离、恢复、重复 request_id、超时与无效输出 | 不重复提交、不污染父分支、不把失败草稿写入正式历史 |
| 上下文 | 对装配模块、可见事实、token 计数和加载范围留证 | 固定配置小于 1,000 tokens；不加载全文或未来节点，不随回合数无限增长 |
| 包完整性 | 根包审计、离散模块审计、lazy runtime 加载 | 哈希、路径、引用一致；加载与校验均通过，不能只查根 JSON |
| 正文质量 | 真实模型中的人物、时间、地点、物品、用户意图与文风实例 | mock/HTTP 成功不替代正文验收；问题必须定位到具体回合 |

首批方向 2 验收至少包含开篇入口与一个已审中段入口，原著角色代入及自由文本行动。原文未支持某角色当时在场时，需要明确的入场设定及其来源，不能通过更换头像假定其已在现场。正式入口若后来改为未知读者模式，应另补“不读原著也能理解开局”的人工测试。

全书自动回归应覆盖所有规范边与重要条件边；真实模型至少抽样每卷一个关键场景、四次跨卷承接、一个持续偏离场景和终局。抽样不是穷举，需要在报告中保留未覆盖范围。

## 六、可复用命令与验证范围

以下是实施阶段命令模板，本轮没有执行写出。`analysis.reviewed.json` 是未来经审核的产物；在审核门槛及新增契约实现前，不应直接运行后半段构建。

```zsh
TAIXU_SOURCE='/Users/James/open-story-engine/docs/太虚遗录-第一部/太虚遗录-第一部-合并.txt'
TAIXU_BUILD_DIR="$(mktemp -d /private/tmp/taixu-story-package.XXXXXX)"

python3 -B -m open_story_engine inspect-source "$TAIXU_SOURCE" \
  --output "$TAIXU_BUILD_DIR/source-manifest.json"
python3 -B -m open_story_engine analyze-source "$TAIXU_SOURCE" \
  --output "$TAIXU_BUILD_DIR/analysis.candidate.json"

# 先完成逐项审核并生成 analysis.reviewed.json，再编译。
python3 -B -m open_story_engine build-story-package "$TAIXU_SOURCE" \
  "$TAIXU_BUILD_DIR/analysis.reviewed.json" \
  --id taixu-relics-part1 --version 0.1.0 \
  --output "$TAIXU_BUILD_DIR/package/package.json"
python3 -B -m open_story_engine audit-story-package "$TAIXU_SOURCE" \
  "$TAIXU_BUILD_DIR/package/analysis.json" "$TAIXU_BUILD_DIR/package/package.json"
python3 -B -m open_story_engine audit-story-package-modules "$TAIXU_SOURCE" \
  "$TAIXU_BUILD_DIR/package/analysis.json" "$TAIXU_BUILD_DIR/package/package.json" \
  "$TAIXU_BUILD_DIR/package/modules"
```

正式执行前再次检查源哈希及包 ID/版本是否存在；不得覆盖同名已发布包。候选产物在独立目录完成审计后才安装到 `content/packages/`。试玩使用临时数据库，已有会话固定原包版本，不进行隐式迁移。

代码实施后的基础检查为 `python3 -B -m unittest discover -s tests_py -q`、涉及 API 时运行 `.venv-api/bin/python -B -m unittest discover -s tests_api -v`，以及 `git diff --check`。真实模型按 [专项评估规范](live-llm-evaluation-v0.1.md) 单独留证。

本轮仅进行了文件计数、哈希与章节对照、`inspect_standard_novel` 和内存中的 `analyze_standard_novel`，以及相关实现的定点阅读。未运行完整回归，未对小说做全量语义审校。
