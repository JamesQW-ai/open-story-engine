状态：设计记录；本文件冻结 Jev 正文审核与剧情补丁的讨论结论，不代表 Jev 已接入，也不代表真实模型或真实长篇游玩已经验收。

## 目标

在正常审核路径不让玩家看到未经确认正文的前提下，减少每回合完整审核、多轮重写和额外等待。模型先生成完整候选正文，Jev 对候选正文和当前上下文做快速、严格、结构化判断；通过后才把正文流式回放给前端。只有用户明确开启的二次失败 fallback，才允许从两次被拒候选中选出通过最低结构守卫且更适合后续补丁的一版回放，并保持状态不变。

上下文管理工程仍是主要质量手段。它负责让模型看到正确的状态、证据、玩家意图和世界观约束；Jev 负责发现上下文治理后仍然出现的规则冲突、事实冲突和可解释性缺口。Jev 不是 StoryPackage、BranchState 或事件账本的权威来源。

## 已确认的生成与审核时序

```text
ContextBundle + BranchState + 玩家输入
                    |
                    v
             模型生成完整正文
                    |
                    v
       服务端暂存候选正文，不发送 delta
                    |
                    v
       Jev 审核正文、结果契约和允许证据
          |                     |
       通过                  严重问题
          |                     |
          v                     v
 本地确定性提交检查       内部修复或重写
          |                     |
          |              二次仍失败且开启 fallback
          |                     |
          |                     v
          |              本地守卫后候选选优
          |                     |
          +---------------------+
                    |
                    v
          提交正文与状态，然后 SSE 回放正文
```

“流式输出”在这里是审核通过后的缓存正文回放。它牺牲了首 token 立即可见，换取玩家不会先看到一段随后被撤回或重写的错误正文。前端可以显示 `generating`、`checking`、`approved` 等状态，但不显示“模型幻觉”“审核失败原因”或内部修复标签。

Jev 审核失败时，常规路径不向前端发送候选正文。可修复问题最多进行一次有边界的内部修复；修复后仍不通过时，默认返回明确失败并保留原始正文、Jev 结果和修复记录。开启 `STORY_LLM_CONSERVATIVE_FALLBACK=true` 后，才进入已确认的二次失败选优路径；选中的正文携带待修补标记，且不允许写入状态补丁。

## Jev 的职责边界

Jev 只做严格、快速、结构化的判断，不负责：

- 修改 `StoryPackage`、`BranchState` 或事件账本；
- 自己决定新的状态变化；
- 代替代码验证实体登记、状态单调性和分支隔离；
- 以文学综合分数覆盖硬事实冲突；
- 通过大段重写直接修正文案。

Jev 可以判断：

- 正文是否兑现本回合 `result_contract`；
- 玩家行动、停止点和转场是否越权；
- 角色是否使用了没有获知路径的信息；
- 是否引用未来 beat、其他分支或未公开作者事实；
- 当前表象是否违反已确认事实或世界观硬规则；
- 轻微异常是否可以由世界观允许的机制解释；
- 后续补丁是否有明确的机制、代价、线索和解释期限。

## 分级裁决

Jev 输出 `decision`、`score`、`issues` 和可选的 `repairDebt`。`score` 用于观测、排序和规则调参，不能单独覆盖严重等级。

| 等级 | 含义 | 默认处理 |
| --- | --- | --- |
| `fatal` | 明确违反硬事实、状态、玩家授权、角色知识或不可改变规则 | `rewrite`；无论分数多高都不能放行 |
| `repairable` | 小范围错误，不影响状态、因果和玩家当前决策，且有可验证的世界观解释路径 | `allow_with_patch`，记录有限期 `repairDebt` |
| `uncertain` | 当前证据不足，不能把候选解释写成事实 | `allow_with_patch` 或要求正文保持模糊 |
| `soft` | 文风、节奏、局部描写或非关键重复问题 | `allow`，可异步记录 |

建议的初始打分仅作为模拟测试起点，不能视为最终阈值：

- 基准分 `100`；
- 每个已确认的 `repairable` 问题扣 `5–15` 分；
- 每个 `uncertain` 问题扣 `3–8` 分；
- `soft` 问题扣 `1–3` 分；
- `fatal` 不依赖扣分，直接将 `decision` 设为 `rewrite`；
- `allow_with_patch` 需要没有 `fatal`、修复债务不超过设定数量、没有状态影响，并达到待校准的最低分数；
- 分数阈值必须通过模拟集和真实短回放校准，不能先把某个固定分数当成质量证明。

建议的 Jev 输出形状：

```json
{
  "decision": "allow|allow_with_patch|rewrite|reject",
  "score": 92,
  "issues": [
    {
      "id": "I1",
      "severity": "repairable",
      "category": "knowledge|state|agency|grounding|world_rule|continuity|style",
      "claim": "正文中的具体问题断言",
      "reason": "为什么判断为该等级",
      "evidenceRefs": ["source-id"],
      "stateImpact": false,
      "patchAllowed": true
    }
  ],
  "repairDebt": [
    {
      "id": "debt-1",
      "direction": "玩家可见的后续调查方向",
      "allowedMechanisms": ["false_death", "avatar"],
      "mustResolveWithinTurns": 2,
      "requiredCostOrClue": "必须解释此前缺席并留下可观察线索"
    }
  ]
}
```

`decision` 的优先级高于 `score`：

1. 任一 `fatal` 直接 `rewrite`。
2. 没有 `fatal`，且存在可控、有限、无状态影响的 `repairable` 或 `uncertain`，才允许 `allow_with_patch`。
3. 没有需要处理的问题时 `allow`。
4. Jev 输出无法解析、超时、低置信或自相矛盾时，不把它当成通过；按回退策略进入本地规则或受控失败。

### 当前冻结的规则适配器

首轮规则已实现为独立的 [jev_review_rules.py](../test_support/jev_review_rules.py)，当前规则版本为 `jev-review-rules/0.3`。OpenRouter Decisions API 的 typed `answers` 先映射为四层结果：L0 硬冲突、L1 原子信号、L2 代码组合的处置、L3 仅用于比较的观测分数。L1 使用正向的 `claim_supported` 判断证据是否支持会影响状态、因果、角色知识或未来事实的具体断言；不改变状态的中性环境、触感或声响描写不应单独触发拒绝。代码把低于 `0.35` 的支持度转换为阻断风险，避免使用负向 `unsupported_claim` 造成模型语义反转。结果增加结构化 `reasonCodes`，用于按证据不足、结果契约缺失、状态冲突、行动越权、知识泄漏、未来泄漏、无支撑断言和补丁支撑不足统计。网络探针只负责请求、响应校验和证据记录，不再自行维护裁决阈值。

当前 `0.65` 仅是首轮风险阈值：任一 fatal 风险或补丁支撑不足达到该值即 `rewrite`。它还不是最终质量门槛；后续必须用更大样本分别校准 fatal 漏检率、repairable 误拒率和长尾延迟。

当前已实现独立的 [jev_gateway.py](../open_story_engine/jev_gateway.py) shadow 适配器。它默认关闭、只发送限定审核字段、无重试，不导入默认 Planner；前置证据失败由本地代码直接拒绝，网络超时、HTTP 错误和结构错误只记录为 shadow 失败，不写入状态。40 个官方章节 beat 加 160 个边界变体的组合层准确率为 100%，重复稳定率为 100%，但尚未完成生成、审核、提交同回合串联，因此不进入默认链路。

## 剧情补丁规则

“剧情补丁”是新增一条可游玩的解释，不是静默改写已确认历史。所有补丁必须同时满足：

1. 不改变已经确认的正文、不可变事实和硬状态。
2. 世界观允许该机制，但“允许提出”不等于“已经发生”。
3. 有机制、代价、限制或可观察线索。
4. 解释此前为什么没有出现、没有被发现或没有产生影响。
5. 有玩家可理解的后续方向和有限的解决期限。
6. 补丁本身不能直接把未知信息写成角色已知事实。

### 可以补丁化的情形

- 已死亡人物再次出现，但正文只描述为疑似本人或相似身影；后续可解释为假死、替身、身外化身或秘术复生。
- 完好物品出现，但没有明确声称它就是此前损坏的唯一原物；后续可解释为仿制品、复制体、借形或诱饵。
- NPC 似乎知道一件事，但正文没有明确写出其已掌握事实；后续可补充传闻、观察、第三方告知或误判来源。

### 必须重写的情形

- 正文明确写出“已确认死亡的人正常存活”，但没有可支持的机制或表象边界。
- 正文明确写出“唯一且不可修复的原物已经恢复”，与硬规则直接冲突。
- 补丁需要修改玩家已经完成的选择、人物生死、物品持有或目标状态。
- 补丁只是为了掩盖模型错误，没有机制、代价、线索和后续目标。
- `repairDebt` 长期累积，无法在约定回合内自然解决。

### 玩家视角约束

剧情方向不得暴露“模型出错”“前后冲突”“内部修复”等信息。方向只描述玩家能观察到的异常、疑问和下一步行动，例如：

> 你对 XXX 的死而复生感到困惑，决定探查他的真实情况。

后续正文再逐步揭示是假死、身外化身、秘术复生、仿制品或其他解释。方向本身不能提前把完整答案写死。

## 本地确定性提交检查是否保留

必须保留，但它不是第二个慢审核模型，而是快速的提交门。它负责检查 Jev 不应拥有的权威事实：

- `ContextBundle` 哈希、package 版本和分支是否匹配；
- 状态变化是否符合父分支和结果契约；
- 新人物、地点、物品是否已经登记；
- 正文关键结果是否与状态投影一致；
- 是否引用未来 beat、其他分支或未公开事实；
- `repairDebt` 是否被正确记录并绑定到当前分支节点；
- 是否存在明确违反硬规则的表述。

这些检查应在服务端缓冲阶段完成，通常不需要额外模型调用。Jev 是快速语义判断层，本地代码是最终状态与持久化权威。

## 下一会话的模拟测试方案

下一会话先不要接真实用户游玩，也不要先修改正式状态。使用最小的模拟 `ContextBundle`、分支状态和正文样本，固定 Jev 版本和提示版本。

### 最小测试矩阵

至少覆盖以下样本：

1. 完全通过：行动、状态、人物知识和世界观均一致。
2. 可补丁的小环境幻觉。
3. 可补丁的假死或身外化身表象。
4. 可补丁的仿制品或复制体表象。
5. 明确违反死亡状态的正文。
6. 明确修复了唯一且不可修复武器的正文。
7. 玩家未授权的移动、交战或决定。
8. NPC 使用没有获知路径的信息。
9. 未来 beat 或其他分支泄露。
10. 世界观允许但缺少机制、代价和线索的解释。
11. 同一正文包含一个可补丁问题和一个 fatal 问题。
12. Jev 返回格式错误、超时、低置信或自相矛盾。

### 必须记录的指标

- JSON 解析成功率；
- `fatal` 误放行率；
- `repairable` 误拒绝率；
- `allow_with_patch` 后补丁是否在期限内解决；
- 分数与人工标签的一致性；
- P50/P95 响应时间；
- 输入输出 token 和单回合调用次数；
- 相同输入的判断稳定性；
- Jev 与本地确定性检查的分歧类型。

第一阶段优先优化 `fatal` 召回率和 `repairable` 误拒绝率，再调分数阈值和文风类规则。模拟通过不能代替真实长篇回放；后续仍需在达标官方长篇的“告知、询问依据、短等待”场景中验证。

## 当前建议

先实现 Jev 的结构化输出契约、分级裁决和模拟测试器；Jev 目前仍以 shadow 方式观察真实回合，尚未成为正式阻断闸门。玩家续写的“审核通过后回放正文”时序已经启用，并独立于 Jev 的最终接入决策。

本方案的目标不是让任何错误都被圆回来，而是让小问题转化为有边界的可玩悬念，让严重冲突在用户可见之前被重写，同时保留 StoryPackage、BranchState 和已确认事件的权威性。

## 延迟优化记录（2026-09-23）

当前正文链路的主要耗时来自多个 DeepSeek 结构化复核串行排队。`action_review`、`scene_grounding`、`scope_review` 只依赖同一份完整候选正文，已在真实 OpenAI-compatible 网关上改为并行；终局分支的两个独立复核也采用同样方式。审核项目、提示和本地硬校验保持不变，假网关测试继续串行以避免共享响应队列失序。`STORY_LLM_PARALLEL_REVIEWS=false` 可在供应商限制并发时关闭。

Jev 当前仍默认是独立 shadow 适配器，尚未成为默认阻断器。已增加可撤回的整回合实验开关：`JEV_RUNTIME_REVIEW_MODE=off|shadow|block`。`shadow` 在本地确定性复核完成后、权威提交前记录 Jev 结果但不阻断；`block` 只接受明确的 `allow`，超时、结构错误、证据不足、`allow_with_patch`、`rewrite` 和 `reject` 均保留原分支并返回可重试错误。实验模式只使用已生成的安全上下文投影，Jev 不写入 StoryPackage、BranchState 或任何状态表。默认仍为 `off`，因此尚未改变当前验收报告中的 `integrated_runtime=false`。

2026-09-24 使用官方长篇和临时数据库完成了一次真实整回合 shadow：writer 生成完成后才调用 Jev，随后才提交分支；总请求约 24715 ms，Jev 833 ms，提交 154 ms，最终分支成功写入。Jev 返回 `allow_with_patch`，因此这次只证明生产时序、审计保存和连通性，不能作为 `block` 模式的通过样本。证据见 [真实整回合 shadow](evidence/jev-narrative-review-2026-09-22/live-runtime-shadow-2026-09-24.json)。

同日又用 3 个边界动作做了真实 shadow 批量复测：1 条完整写入，服务端内部首段为 20887 ms，但审核、提交完成后的用户首字为 33110 ms，Jev 返回 `allow` 并耗时 819 ms；另 2 条分别在 writer 的二次复核和初始生成阶段失败，总耗时 46551 ms 与 14713 ms，用户首字均为 0，且都未调用 Jev、未写入分支。该批次确认 runtime gate 的顺序和失败时的分支保护，但只有 1 个 Jev 样本，不能用于估计 Jev 质量或 P50/P95；block 模式继续关闭。证据见 [真实 shadow 批量复测](evidence/jev-narrative-review-2026-09-22/live-runtime-shadow-batch-2026-09-24.json)。

正式接入时，候选正文完成后应让 Jev 与本地确定性复核并行，二者都完成后才允许权威提交；这样可以把 Jev 的等待与本地复核重叠，而不是继续累加。不能通过减少 fatal、agency、knowledge、future 和 grounding 检查来换取延迟下降。

### 2026-09-23 真实延迟复测

在 `taixu-relics-part1@0.1.3`（102610 CJK）上用 5 个不同动作做了直连 `deepseek-v4-flash` 批量复测，临时数据库与 `STORY_LLM_PARALLEL_REVIEWS=true`，没有修改正式 `.env`。5 条中 1 条成功提交，耗时 25189 ms；4 条最终 `generation_failed`，耗时 14669–56915 ms。失败请求均保留了候选和类型化调用记录，未写入分支；失败原因包含模型输出被事实／知识边界校验拒绝、后续重试未形成可提交计划，以及 provider 传输回退，不能简单归因于 Jev。完整记录见 `docs/evidence/jev-narrative-review-2026-09-22/live-writer-latency-batch-parallel-2026-09-23.json`。

同一真实自由行动又做了一次提交前 Jev shadow：writer 使用 `deepseek-v4-flash`，候选生成后调用 Jev，再提交故事状态；总耗时 50746 ms，其中 Jev 5831 ms、提交 216 ms，最终写入成功。Jev 返回 `allow_with_patch`，L0 通过，L3 最低观察分 65；该调用仍是隔离 monkeypatch，未接入生产提交路径，也不阻断写入。证据见 `docs/evidence/jev-narrative-review-2026-09-22/live-precommit-shadow-parallel-2026-09-23.json`。

本轮结论是：并行复核代码已经生效，可以消除同一候选的独立审核串行排队；但真实用户等待的主要长尾仍来自 DeepSeek 多轮重试和 provider 波动。Jev 单次约 5.8 秒，后续正式接入应与本地确定性复核并行，并设置可撤回的超时回退；在 writer 首稿通过率和失败分类稳定前，不应把 Jev 改成阻断闸门。结构化 JSON 预算 4096 的临时对照曾增加语义拒绝，继续保持默认 8192，不用缩减预算换取未经验证的速度。

正文与审核现在使用分离的输出预算：玩家正文当前配置为 `STORY_LLM_TEXT_MAX_TOKENS=2048`，结构化规划和审核继续使用 `STORY_LLM_MAX_TOKENS=8192`。正文契约上限为 1500 个汉字，收紧正文预算可减少无效生成尾部；审核 JSON 不跟随收紧，避免把语义审核失败误判成延迟优化。

2026-09-23 的同路由单回合 A/B 将正文预算切换为 `STORY_LLM_TEXT_MAX_TOKENS=2048`：官方长篇直连 `deepseek-v4-flash` 在临时数据库中审核通过并写入，用户首字为 23384 ms；此前同类 4096 对照为 39974 ms。该优化只收紧正文输出预算，结构化规划与审核仍保持 8192，且正文仍在审核和权威提交完成后才回放。证据见 [2048 正文预算首字对照](evidence/jev-narrative-review-2026-09-22/live-first-visible-2026-09-23-text-budget-2048.json)。

## 三种审核结果的用户可见时序（2026-09-23）

续写候选现在完全在服务端缓冲，`TurnDrafts.wait` 不再向客户端转发生成中、修复中或 `retained_draft` 的事件。只有候选完成审核、通过本地确定性提交并成功写入分支后，`replay_approved` 才把已确认正文分块回放给客户端；因此不会出现“先看到正文、审核失败后再推翻”的体验。

1. **首轮通过**：一次生成和审核，提交成功后回放最终正文。
2. **首轮失败**：最多执行一次有界修复/重写；修复期间保持不可见，只有修复后的完整候选通过审核并提交后才回放。
3. **二次仍失败**：不再继续付费重写。用户已确认放宽这条路径的语义门禁：`STORY_LLM_CONSERVATIVE_FALLBACK=true` 时，服务端保留两次完整审核失败的候选，先执行本地结构守卫，再按问题严重度、问题数量、待修补范围和篇幅边界选出更适合后续补丁的版本，直接回放选中的正文。选优候选仍必须满足正常交互正文的 80 个 CJK 字符下限和 1500 个上限；低于下限的短候选不会被选中，避免重现 54 字正文体验。该正文会标记为 `candidate_selected_pending_patch`，审计中保留候选摘要、问题类型和哈希；它不产生状态补丁，权威 `BranchState` 仍复制父分支，后续补丁必须重新通过完整审核才能改变状态。若两个候选都无法通过最低结构守卫，才退回本地确定性的三段式保守正文（`conservative_approved`）；它只复制父分支的已确认状态和已公布方向，使用空状态补丁，并再次经过本地叙事守卫、可选 Jev 审核和权威提交后才回放。关闭该开关时仍返回 `retryable=true`、`candidateShown=false`、`previousBranchUnchanged=true` 的安全失败。

该时序优先保证叙事连续性和用户信任；延迟优化应在此边界内进行，重点放在首稿稳定性、复核并行和超时分级，而不是提前发送未经审核的正文。
