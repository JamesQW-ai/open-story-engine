# LLM 质量链路 v0.1

## 设计目的

借鉴开源小说生成系统常见的“规划 -> 正文 -> 一致性审阅 -> 修订 -> 沉淀上下文”分阶段思路，本项目在现有 Planner 后增加可选的叙事质量审阅。借鉴的是架构模式，不复制第三方代码；参考项目 `YILING0013/AI_NovelGenerator` 使用 AGPL-3.0，不能将其实现直接并入本仓库。

质量链路的目标是提高因果、角色、细节、场景与下一步互动感，不把它当作状态机或事实来源。

## 顺序

```text
已公布方向 + 已确认 BranchState
  -> Planner 生成正文草稿
  -> 确定性结构/状态/叙事事实校验
  -> 可选 NarrativeReviewer
  -> accept: 追加 BranchNode
  -> revise: 把具体问题交给 Planner 重写一次，再校验
```

`STORY_LLM_QUALITY_REVIEW=false` 为默认值。启用时才新增一次审阅调用：

```dotenv
STORY_LLM_QUALITY_REVIEW=true
```

审阅失败、超时或结构无效时不允许持久化草稿。真实模型调用仍需人工授权，默认自动测试只运行 Mock。

无论是否启用审阅，正文 Planner 对无效 JSON、缺字段或章节名称、未公布方向、无推进补丁、不支持的状态枚举、受控路线不成立、未登记的人物姓名或已确认状态矛盾都会带着具体原因自动重试一次。两次都失败时草稿不会写入分支；`llm-audits` 会保留每次 transport 尝试与最终失败原因。Mock 的短固定文本只服务离线契约验证，不能用来评价模型写作质量。

## 动态章节尺度

Planner 提示将约 1,800 至 2,800 个中文字符作为通常场景目标，而不是运行时硬阈值。有效的悬念、章节收束、场景转场或高张力停顿可以自然更短或更长；审阅器看的是是否有承接、行动、阻力、细节和可交互的新压力，而非机械计数。

每个已确认分支必须有 `storyArc.chapter.title`；CLI 会在正文确认后与主线目标、当前阶段一并显示。流式草稿尚未解析完结构化章节字段时不把临时标题当作已确认信息。

## 新人物与身份

新人物可先以称谓、行为或线索出现。身份、职业、动机不是首次出现时的必填字段，只有后续分支确实揭示时才追加 `derivedCharacterReveals`。审阅器不能因为身份暂未揭晓而把草稿误判为不一致。

## 不可跨越的边界

- `StoryPackage`、不可变事实和规范原文不由模型写入。
- `BranchState` 的单调状态、地点与场景路线仍由确定性代码校验。
- 模型不可把尚未选择的行动、未取得证据、未完成救援或未发生的列车状态写成事实。
- 流式 `narrativeText` 仅显示为“生成中，尚未提交”的草稿；审阅和全部校验成功后才追加分支。
- 兼容网关将段落双重转义为字面 `\\n` 时，CLI 在草稿显示与提交前都将其还原为真实换行；这不改变正文的其他字符。
