# LLM 质量链路 v0.1

## 设计目的

借鉴开源小说生成系统常见的“规划 -> 正文 -> 一致性审阅 -> 沉淀上下文”分阶段思路，本项目在现有 Planner 后增加可选的叙事质量审阅。审阅只记录问题，不以自动修订覆盖玩家刚刚选择的回合。借鉴的是架构模式，不复制第三方代码；参考项目 `YILING0013/AI_NovelGenerator` 使用 AGPL-3.0，不能将其实现直接并入本仓库。

质量链路的目标是提高因果、角色、细节、场景与下一步互动感，不把它当作状态机或事实来源。

## 顺序

```text
已公布方向 + 已确认 BranchState
  -> Planner 生成正文草稿
  -> 确定性结构/状态/叙事事实校验
  -> 可选 NarrativeReviewer
  -> accept/revise: 追加 BranchNode，并将审阅意见写入 audit
```

`STORY_LLM_QUALITY_REVIEW=false` 为默认值。启用时才新增一次审阅调用：

```dotenv
STORY_LLM_QUALITY_REVIEW=true
```

审阅失败、超时或结构无效时不影响已通过确定性校验的正文持久化；审阅结果只是后续人工质量分析的审计信息。真实模型调用仍需人工授权，默认自动测试只运行 Mock。

每次玩家选择只对应一次正文 Planner 草稿生成，不会因 JSON、章节名称、方向、路线、人物登记或状态事实问题发起第二次正文重写；传输层在 SSE 首段正文超时时仍可发起兼容 JSON 回退。摘要、章节信息和后续菜单中可安全修复的局部字段可由运行时归一化；已声明并通过校验的分支私有地点、人物、物品及身份揭示会随该草稿写入状态。不可安全修复的 JSON 或叙事状态矛盾会拒绝该草稿且不写入分支；`llm-audits` 会保留传输回退、归一化与最终失败原因。Mock 的短固定文本只服务离线契约验证，不能用来评价模型写作质量。

## 动态章节尺度

Planner 提示将约 1,800 至 2,800 个中文字符作为通常场景目标，而不是运行时硬阈值。有效的悬念、章节收束、场景转场或高张力停顿可以自然更短或更长；审阅器看的是是否有承接、行动、阻力、细节和可交互的新压力，而非机械计数。

每个已确认分支必须有 `storyArc.chapter.title`；CLI 会在正文确认后与主线目标、当前阶段一并显示。流式草稿尚未解析完结构化章节字段时不把临时标题当作已确认信息。

## 新人物与身份

新人物可先以称谓、行为或线索出现。需要跨回合引用的角色、地点，以及会影响行动、取证或因果的物品，都必须在首次出现的正文结果中以 `branchAdditions.characters`、`branchAdditions.locations` 或 `branchAdditions.items` 登记；它们只属于当前分支，不改写来源 `StoryPackage`。身份、职业、动机不是首次出现时的必填字段，只有后续分支确实揭示时才通过 `branchAdditions.characterReveals` 追加一次。审阅器不能因为身份暂未揭晓而把草稿误判为不一致。

## 不可跨越的边界

- `StoryPackage`、不可变事实和规范原文不由模型写入。
- `BranchState` 的单调状态、地点与场景路线仍由确定性代码校验。
- 模型不可把尚未选择的行动、未取得证据、未完成救援或未发生的列车状态写成事实。
- 流式 `narrativeText` 仅显示为“生成中，尚未提交”的草稿；审阅和全部校验成功后才追加分支。
- 兼容网关将段落双重转义为字面 `\\n` 时，CLI 在草稿显示与提交前都将其还原为真实换行；这不改变正文的其他字符。
