# 任务转交：玩家方向输出正向兑现 + 缩短等待

日期：2026-09-17\
用途：转交 Codex 执行。规划记录不等于完成验收。

## 产品约束（本任务内固定）

- **不考虑 token/调用费用预算**（自有 API，文字生成消耗可忽略）。
- 仅开发桌面端；官方长篇冻结包为验收母本，不改母本身份。
- 不得伪造正文、假进度或绕过事实/状态校验写入分支。
- 权威状态仍只在校验通过后写入；但**用户可见响应不得因审查失败而消失**。

## 实际目标（按优先级）

### P0 — 方向必须被正文正向兑现（最高）

**定义：** 玩家选择/自定义输入一个方向后，下一回合输出必须**在叙事与权威状态上同时体现该方向的明确后果**，不能默默改写、弱化或悬置。

**硬例子：**

- 方向=「杀掉角色 X」→ 正文须以合乎场景逻辑的方式写 X 死亡，且权威状态 `characterOutcomeStates[X].status = dead`，后续菜单/互动不再把 X 当可行动对象。
- 方向=「离开地点 A」→ 正文写清离开，且 `playerLocationId` 变为目标地点。
- 方向=「放弃目标 G」→ 正文交代放弃，目标账本状态与正文一致。

**成功后置条件（缺一不可）：**

1. 正文明确呈现该后果（有因果，不是一句带过或与行动矛盾）；
2. 权威状态/账本已登记对应结果；
3. 后续回合不复活、不串线（死亡/永久离队等不可逆项）。

**失败时：**

- 必须给用户**可见反馈**（未确认草稿或明确失败原因 + 重试），禁止只丢一句无上下文的 `generation_failed`；
- 不得静默改成「击退/受伤/暂时离开」等更弱后果。

**验收：** 固定官方长篇 + 固定身份 + 固定输入（至少覆盖：击杀、离开、放弃目标、询问、等待各 1 条），连续多回合记录：正文证据、状态 diff、是否一次通过、修复次数、总耗时。

### P1 — 用户操作必须有正向/可恢复的响应

- 每次提交方向后，界面/API 必须有结果：
  - **通过** → 确认正文 + 状态已更新；或
  - **未通过** → 保留可读草稿（如有）+ 失败阶段说明 + 重试入口。
- 写前规划/审查失败时，**自动重规划**（可多次，费用不敏感），仍失败才降级回执，而不是零正文直接失败。
- 审查打回策略分层：
  - **硬后果**（死亡/损毁/地点/目标/永久离队）必须严校验；
  - **非关键文风/复述**不得单独导致整回合打回。

### P2 — 尽量缩短输出等待时间（在 P0/P1 达标前提下）

- 换直连后的官方生产档模型（确认正式 model ID，避免 flash 吃光正文预算）。
- 减少串行深度：规划/授权/正文职责清晰，避免同一目标上「审查→修复→再审查」无限叠层。
- 可接受手段：并行候选草稿、预生成方向、正文优先流式首字、限制修复为「单目标一次修」。
- 指标：首字时间、完整正文时间、方向菜单可用时间；目标是**可感知变快**，不是无限等待。
- **禁止**用无限超时/无限重试伪装「更快/更稳」。

## 明确不做什么

| 不做 | 原因 |
|------|------|
| 把「加预算、加长超时」当最终修复 | 只延迟失败，不保证方向后果兑现 |
| 无上限提高调用次数作为永久方案 | 可作实验对照，不可作为产品默认 |
| 放宽硬后果校验换通过率 | 会导致击杀变击退等语义漂移 |
| 重做故事解析包/冻结母本 | 当前无响应与方向不兑现主因不在包结构 |
| 用假正文/模板扩写制造「有输出」 | 违反产品与验收边界 |
| 继续只堆知识边界提示词 | 近几天已证明无法单独解决失败闭环 |

## 失败闭环（修复时对着打断）

```text
方向输入（如：杀 X）
  → 规划/初稿未正确兑现后果 或 语义不稳
  → 严审打回（含非关键问题）
  → 修复再偏/再被拒
  → 预算或等待耗尽
  → generation_failed，用户看不到已确认后果
```

**打断点：**

1. 规划阶段就把「必须兑现的后果」写进结果契约并当硬校验；
2. 非关键问题不触发整回合失败；
3. 失败必有可见响应；
4. 修复只对准硬后果，不整篇重写。

## 根因分层（与既有审查一致）

| 层级 | 角色 |
|------|------|
| 根因 | 模型对知识边界、人物状态、用户意图语义理解不稳 |
| 加速器 | 审查过严 → 误拒 → 修复再出错 → 再打回 |
| 放大器 | 调用预算用尽、超时/等待不够 → 整回合判失败 |

预算与响应时长是失败的**放大器**，过严审查是**加速器**；调大预算、延长超时只能作为对照实验，不能作为最终修复。单回合现有记录中的等待上限为 **120 秒**（不是 120 毫秒），对当前长提示与多轮审查仍可能不够，但「已拿到完整响应仍误判」不能用超时解释。

## 建议执行顺序（给 Codex）

1. **固定输入对照实验（先测后改大）**\
   同一「杀 X / 留下 / 放弃」输入，分别记录：当前预算、放宽调用次数、放宽非关键校验、官方模型+直连——对比初稿是否正确、最终是否正文+状态双通过、误拒率、耗时。
2. **实现 P0 后置条件**\
   明确后果 → 正文证据 + 权威状态 + 后续不可逆；失败禁止静默弱化。
3. **实现 P1 响应契约**\
   有稿必展示；写前失败自动重规划；硬/软校验分层。
4. **实现 P2 延迟**\
   模型与传输、串行削减、并行/预生成；用耗时指标验收。
5. **桌面连续试玩**\
   官方长篇、固定身份，覆盖方向兑现 + 有响应 + 等待时间，写清通过/未通过边界。

## 验收口径（汇报可用）

- **P0 通过：** 固定「击杀」等方向，连续回合中文本与状态均兑现，且不可逆项不复活。
- **P1 通过：** 任意提交都有确认结果或可恢复失败反馈，无「无正文且无说明」的死路。
- **P2 通过：** 相对当前基线，首字/完整正文可测量下降；未达标要写明原因，不拿无限等待充数。
- **不宣称：** NQ-001 全部文学质量问题已关闭；本任务以「方向正向兑现 + 有响应 + 等待」为准。
