# MVP 技术方案

## 决策状态

本文是当前 MVP 的实现基线。范围是单机 CLI 原型，用一个人工整理的预置故事包验证“上下文装载 -> 玩家行动 -> 检定 -> 状态更新 -> 叙事呈现”闭环；它不是最终玩家端的界面方案。

## 目标与非目标

目标：验证互动叙事引擎能在自由文本输入下保持状态可信、剧情可追溯和阅读节奏可控。

非目标：任意小说上传与解析、Web 界面、图片生成、多用户、云端部署、开放世界和无限内容生成。

CLI 是开发验证工具。正式玩家端将以“小说阅读器 + 自由行动区”为中心，而不是复用命令行界面。

## 技术选型

| 领域 | 选择 | 原因 |
| --- | --- | --- |
| 运行时 | Node.js 22 LTS | 当前开发环境为 `v22.23.2`，适合后续前后端共用 TypeScript 领域模型。 |
| 语言与模块 | TypeScript，ESM | 在编译期约束状态、事件与内容契约，避免 CLI、引擎和未来 Web 层出现类型漂移。 |
| CLI | `commander` + `@inquirer/prompts` | 提供可脚本化命令与适合人工试玩的交互输入。 |
| 数据校验 | `zod` | 在读取故事包、写入状态、解析 LLM 输出时执行同一份运行时校验。 |
| 本地存储 | SQLite + `better-sqlite3` | 零部署，支持原子事务、本地存档和可审计事件历史。 |
| 测试 | `vitest` | 快速验证规则、回合服务和存档重建。 |
| LLM 接入 | 自定义 `LlmGateway` + OpenAI-compatible 适配器 | 不让领域代码依赖特定供应商；开发期可使用 `mock` 实现稳定测试。 |

不在 MVP 中引入 Web 框架、ORM、向量数据库、工作流编排框架或多智能体系统。它们解决的规模问题尚未出现，反而会掩盖叙事规则是否成立。

## 系统边界

```text
CLI
  -> TurnService
       -> ActionParser (LLM)
       -> RuleEngine (代码，权威判定)
       -> SQLite transaction (事件与状态)
       -> ContextBuilder
       -> Narrator (LLM)
```

`RuleEngine` 是唯一可决定状态变化的组件。LLM 只能：

- 将玩家自然语言转换为受 schema 限制的行动意图。
- 在给定的已确认事实、检定结果和状态变化范围内生成叙事文本。

LLM 的任何 JSON 输出都须经 `zod` 校验。校验失败时不得写入状态，回合应返回可恢复错误，并将原始输出写入审计记录。

## 回合与状态一致性

每个回合按固定顺序执行：

1. 读取当前会话快照与故事包。
2. 解析玩家意图，得到受限的 `ActionIntent`。
3. 根据前置条件、角色属性、随机检定和预置规则计算 `Resolution`。
4. 在一个 SQLite 事务中追加不可变事件并写入新状态快照。
5. 将已确认的 `Resolution` 交给叙事器生成正文。
6. 保存叙事结果与 LLM 审计信息；叙事写入失败不回滚已完成的游戏判定，但必须标记该回合待补全。

MVP 状态使用经 schema 校验的 JSON 快照：属性、背包、关系、旗标、当前节点和已知事实都在一个版本化对象中。`game_events` 保存每次输入、行动、检定、状态差异和正文，使快照可重建、错误可定位。现在不把背包或关系值拆成大量表；需要跨存档查询时再增加读模型。

## 故事包契约

首版只加载一个人工创作或已获授权的预置 `StoryPackage`。它不能是未经整理的整本小说文本，应包含：

- 基础元信息与版本。
- 世界规则、不可违背事实和写作风格提示。
- 角色、地点、物品和初始关系。
- 已发生事件与时间线。
- 主线锚点、章节目标、可达结局和起始场景。
- 可由规则引擎执行的行动、前置条件和结果模板。

未来“用户导入小说”应产生待审核的候选 `StoryPackage`，而非让引擎直接消费原文。这样可隔离版权/授权、解析质量、用户确认和故事一致性等问题。

## LLM 上下文与成本控制

每次调用只包含：故事包的相关片段、当前状态、当前章节目标、近期少量事件和已确认事实摘要。禁止将整本小说或全部对话历史直接拼接进提示词。

设置明确上限：输入上下文预算、输出字数、重试次数和每回合调用次数。MVP 默认最多两次调用：一次行动解析、一次叙事生成；`mock` 模式下不调用外部服务。

应记录模型标识、提示词版本、请求摘要和原始响应，用于评估幻觉、成本和可复现性。密钥只来自环境变量，不进入 SQLite、Git 或日志正文。

## 目录方案

```text
src/
  cli/
  application/
  domain/
    rules/
  content/
  infrastructure/
    db/
    llm/
  shared/
tests/
docs/
data/                # 运行期 SQLite 文件，Git 忽略
```

领域代码不得直接依赖 `commander`、SQLite 或具体 LLM SDK；这些依赖只存在于 `cli/` 和 `infrastructure/`。`content/` 的故事包必须能够被测试单独加载和校验。

## 首个实现切片

首个代码提交只覆盖以下能力：

1. 初始化 Node.js / TypeScript / Vitest 项目及基础命令。
2. 创建一个小型预置故事包和对应 `zod` schema。
3. 创建 SQLite 会话、快照、事件和审计表。
4. 实现三种固定行动的确定性检定与状态更新。
5. 提供 `mock` 叙事器和 `play`、`status` 命令。
6. 用测试证明非法状态不能写入，事件可重建状态，叙事器不能改变检定结果。

真实 LLM 适配器、首个完整章节与玩家端 UI 均在该切片通过后再进入。
