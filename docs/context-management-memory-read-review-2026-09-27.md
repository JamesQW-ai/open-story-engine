## 本轮交付

新增 [dynamic_memory_read_benchmark.py](../test_support/dynamic_memory_read_benchmark.py)，在既有物品纯内存测量之外，覆盖两类账本累积：每四回合新建三个目标/问题，再关闭其中最新一个。原记录保留，既包含累积，也包含旧状态被新状态替代。

每档使用官方达标长篇的不同原始段落，构造 32、128、512 回合；当前母本为《太虚遗录》`0.1.3`、102610 汉字。状态与审核记录仍是合成成本夹具，段落不证明合成目标变化已获剧情授权，不能用于正文质量或真实后果验收。未调用模型、Jev、生图接口，也未写正式会话。

全部数据库由 `TemporaryDirectory` 管理，夹具拒绝复用已存在的库。准备阶段用 `SessionStore` 写入并关闭，测量阶段只通过 API 使用的 `ReadService.store()` 开启只读 SQLite 快照，不运行初始化或迁移。数据库准备不计入读取耗时。

## 测量范围

| 阶段 | 实际执行 |
| --- | --- |
| `readMs` | 新建只读连接、开启事务、`lineage` 查询与 JSON 解析、关闭连接 |

每档重复五次，保留逐次数据、各阶段中位数和最近秩 P95；五次的 P95 即最大值，不是稳定服务级指标。每次使用新数据库连接；操作系统文件缓存不清除，第一轮 resolver 模块缓存为空，之后复用，因此第一轮与后续轮的缓存条件不同。各阶段中位数之和不一定等于总耗时中位数。

该路径测到数据库至上下文投影，但**不是完整 API 回合延迟**：不包含包加载、`_turn_snapshot` 的会话/合同/收束检查、最终预算器、模型调用、审核、提交和前端显示。夹具也未逐轮累积完整 `branchLedger`、全部审核和其他实体变化，因此不能当作生产存储成本上限。

| goal | 32 | 1.756 | 0.643 | 1.855 | 1.225 | 0.158 | 5.828 |
| goal | 128 | 14.537 | 0.650 | 7.544 | 3.143 | 0.359 | 26.343 |
| goal | 512 | 299.307 | 0.681 | 36.987 | 10.178 | 1.155 | 348.737 |
| thread | 32 | 1.919 | 0.665 | 1.905 | 1.266 | 0.161 | 6.118 |

| thread | 512 | 181.257 | 0.672 | 36.450 | 11.171 | 1.220 | 229.881 |

512 回合临时库分别约 40.6 MiB、43.1 MiB，实际分支 JSON 为 42,010,123 / 44,667,657 字节，最后分别有 384 个目标、386 个问题（含原入口问题）。单次 lineage 均执行 513 次 SELECT。goal/thread 延迟差异不能直接解释为类型成本差异，尚未控制内存分配、GC 与系统负载。

一次临时 CPU 归因采样也显示 JSON 解析占读取开销的大头；该诊断未纳入正式重复测量。问题不只是 SQL 调用次数：随目标数增加，每个历史分支又保存一份当时的账本，累计 JSON 负载随回合数增长得更快。

选择器与写作投影没有把全部账本转为正文上下文：固定查询只装入对应的 1 条确认记忆；本轮各长度写作投影约 4.7 千字符。长度间原著段落不同，不能把投影字符的微小波动当作压缩收益。

[最终证据](evidence/context-management-2026-09-22/memory-read-final-2026-09-27.json)包含各次结果、查询数、字节数与源文件哈希，已逐项核对哈希。[首轮证据](evidence/context-management-2026-09-22/memory-read-baseline-2026-09-27.json)保留。两份记录用于复测成本，不是生产改动的前后加速对照。

## 已修复：回合准备重复读取

`PlayService._turn_snapshot` 原先自行读取 lineage，随后 `journey` 与 `store.closing_intent` 又各读取一次。现在路线检查直接调用既有 `route_status`，收束检查调用既有 `route_lifecycle.closing_intent`，均使用本次只读事务已读取的 lineage，不再生成用不到的历程展示数据。

回归验证每次 `_turn_snapshot` 从三次历史读取降为一次；两次相同请求仍执行两次独立读取，即缓存命中不跳过当前状态校验。路线状态计算仍使用原有逻辑，父分支结束后子分支也被拒绝；收束意图变化影响缓存绑定，损坏意图返回 `route_history_unavailable`。没有引入跨请求历史缓存。

上表没有调用 `_turn_snapshot`，因此不把三次降为一次换算为整体提速百分比；完整回合的模型、审核及提交延迟尚未重测。

## 不变性验证

- 数据库还原出的完整 lineage 与固定输入逐项相同；同一输入多次生成相同 bundle 哈希。
- 固定查询只选预期来源，仍受 4 条/800 字符限制；`chapter.dynamicMemory` 保留该记忆，`allowedEvidence` 不重复注入同源短事实。
- 数据库文件在测量前后 SHA-256 相同，内存输入也不改变；测试令 `_initialize` 直接抛错，读取至投影仍能完成。
- 当前来源被篡改后省略该记忆，不能重新启用已结束问题的旧 open 记录；兄弟分支不进入当前 lineage 或 bundle。
- 夹具使用不同的官方原文段落，不以重复模板凑长度；身份/时间固定，输入可复现。无效长度、重复次数、类型及已存在数据库均明确拒绝。

本轮测量/记忆/bundle 定向测试 84 项通过；回合准备与收束定向测试 16 项通过；最终完整 API 回归 498 项通过（111.221 s）。各组存在重叠，不能相加为独立用例总数。`git diff --check`、文档相对链接及最终测量源文件哈希检查通过。

本轮未重跑完整 core；先前记录的 `consequences.plan` 提示哈希失败未处理，不通过重写历史基线消除。未改前端，未调用真实模型，不宣称真实质量或全工程验收通过。

## 后续清单

当前证据不支持通过扩大记忆预算、删除旧来源或跳过审核来优化。建议按以下可验收顺序推进：

1. 已完成 `_turn_snapshot` 同事务去重；继续盘点模块解析和正文审核所需历史字段。用固定输入补完整回合准备的前后配对测量，区分读取、路线检查和快照构造，不把局部成本外推为全链路收益。
2. 单次读取仍是当前测量主因。下一项设计只读历史视图或有界检查点/增量状态方案，先比较完整还原和兼容成本，再决定实施。新方案必须完整还原旧格式的正文、父关系、审核凭据和状态；正式库迁移须单独给出可审核方案，当前不直接改写历史存储。
3. 任何候选优化都与本次固定输入配对：lineage 内容、记忆来源、生命周期审计、bundle 和 chapter 哈希一致；来源/状态变更下一次读取立即生效；循环、断链、跨会话、兄弟分支、v1/v2 兼容、事务回滚均不放松。
4. 在 32/128/512 回合两类负载上同时报告查询数、实际解析字节、分阶段耗时和注入大小；保持失败记录，不能仅凭一次最快结果宣称提速。
5. 正式语义纠错/候选拒绝业务契约，以及真实正文—审核—修复—提交验收仍单独待做。上下文工程通过后再进入既定剧情配图阶段。
