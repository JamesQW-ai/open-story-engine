## 开发目标

将《太虚遗录》第一部的故事包做成可靠的游戏初始内容与规则数据包，并接入现有生成链路，让用户选择方向后，正文能够承接人物、世界、物品、知识和已发生事件，保持可读性与因果一致性。

成功标准分成两层：故事包本身完整、可信、可编译；使用这个包生成的连续正文可理解、体现用户意图、没有关键事实矛盾。第一层通过不自动证明第二层通过。

本文件将 [故事包构建规划](taixu-story-package-plan-2026-09-14.md) 拆成开发任务。五模块定义、母本统计和原文风险沿用该文件；本计划新增实现顺序、代码责任、测试场景及交付门槛。本轮只新增计划文件，各开发任务均尚未开始。

## 范围与实施原则

- 输入固定为第一部 50 章合订本。本轮复核 SHA-256 仍为 `61efaffb17d652ccc0fcb15b98a133fd976296d342966c0a426b7831f9810904`。不使用七千余字旧稿，不纳入第 51 章以后的续篇。
- 开发主线为“内容审核与编译 → 当前上下文 → 分支状态 → 正文规划与校验 → 首卷验证 → 全书扩展”。复用已有 Python 核心和 API，不另建一套引擎。
- 官方包保存固定内容、规范演变和互动规则；当前局的实际变化进入私有分支。生成摘要、模型回答和阅读笔记不能成为权威状态的替代品。
- 先建立全书目录、实体目录和候选因果骨架，再完成首卷所需内容的审核与可玩验证。其余章节可以保留明确待审状态，但不得参与首卷可执行约束。
- 人名纠错、地点与物品标注放在内容输入层；只有可复用的编译、加载和校验逻辑进入引擎。不往通用代码中新增“陆照临专用规则”。
- 每次迭代交付可检查的产物和结果；确定性的证据核对连续执行，无法从原文裁决的冲突集中提交，不逐章等待确认。不把 Agent 复核记成人工审核。
- 产品入口冲突仍按前一规划登记。本任务显式 `AGENTS.md` 的方向 2 作为默认集成验收口径，不在本开发包中改造书库或删除入口。

## 目标处理链路

```text
母本快照 + 带来源的审核标注
  → Python 编译与双层审计
  → 版本化 StoryPackage

StoryPackage + 入口前史
  → 初始分支状态
  → 用户方向 / 自由文本
  → 当前可见上下文 + 行动意图
  → 剧情方案与候选状态变化
  → 本地规则验证
  → 正文生成与验收
  → 原子提交事件、正文和分支状态
  → 下一回合
```

候选状态可用于撰写本次正文，但在本轮完整通过前不提交。失败恢复应保留原分支和请求身份，不能出现正文失败却已经转交道具的半完成状态。具体事务接点需适配现有共创链路，不强制重写历史 CLI 的处理方式。

## 迭代顺序与里程碑

按结果安排迭代，不预先承诺日历工期。十万字审校与真实模型返工的工作量尚未测定，第一轮结束后依据候选错误数量与首场景验证成本更新估算。

| 迭代 | 主要结果 | 核心依赖 | 完成后可确认什么 |
| --- | --- | --- | --- |
| D0 输入基线与审核入口 | 可追溯的全书输入、候选与审核记录 | 当前合订本 | 后续所有产物能追到相同版本 |
| D1 五模块契约与内容标注 | 全书候选骨架、首卷已审核数据、长篇扩展规范 | D0 | 谁、在哪里、知道什么、拥有什么以及变化条件可检查 |
| D2 编译器与首卷包 | 可重复编译、双层审计通过的首卷候选包 | D1 中首卷及其引用内容通过 | 包能被引擎正确加载，未开放内容不会被使用 |
| D3 上下文与状态联动 | 可见信息投影、道具/知识/线程状态变化与恢复 | D2 | 用户选择产生正确、持久、分支独立的后果 |
| D4 正文质量闭环 | 意图、方案、正文、验收和有限修复接通 | D3 | 连续正文能承接本局选择，失败可恢复 |
| D5 第一卷验收 | 第 1–10 章完整切片、至少一个完整 Arc 的真实模型证据 | D4 | 第一卷可玩与可读，不代表全书通过 |
| D6 全书扩展与候选发布 | 五卷及跨卷因果、终局、版本交付 | D5；末卷冲突关闭 | 50 章范围的内容与运行证据齐备 |

这组迭代细化前一文件的 P0–P5：D0 对应候选冻结，D1–D2 落实内容与编译契约，D3–D5 落实首卷运行验证，D6 落实逐卷扩展及全书验收。

## D0：先把输入和审核入口做可靠

| 任务 | 工作内容 | 产物 / 文件责任 | 验收 |
| --- | --- | --- | --- |
| DEV-001 | 建立字节级源快照、分章哈希与段落映射；登记旧稿排除和第 41–44 章问题 | 拟新增 `content/authoring/taixu-relics-part1/<source-revision>/` 内的清单与问题单 | 源文件无改动；50 章覆盖；任何引用可反查原句 |
| DEV-002 | 保存候选分析并生成纠错清单，不丢失被拒绝候选 | 同目录 `analysis.candidate.json`、实体纠错表 | 明确列出人名截断、伪人物、关键实体遗漏及空事件章节 |
| DEV-003 | 定义审核记录与输入绑定，支持接受、纠正、拒绝、待审 | 内容审核契约文档及审核数据；`package_builder.py`/`cli.py` 的最小接入 | 源哈希或候选内容改变后，旧审核失效；不能只把顶层 status 改成 approved 就放行 |

审核记录至少保存源哈希、候选 ID、证据段落、裁决、修订内容、审核者类型与标识、审核时间。另存逐项裁决集合的哈希，使构建输入可追溯。审核身份只记录真实执行方，不伪造人工签字，也不引入当前不需要的完整账户系统。

第一批开发建议只执行 DEV-001～DEV-003：它们既能形成实际内容材料，又能先阻止错误候选被当作权威信息；无需等待全部长篇运行功能完成。

## D1：固定五模块的数据和行为契约

| 任务 | 工作内容 | 交付物 | 验收 |
| --- | --- | --- | --- |
| DEV-004 | 建立全书角色与别名目录；审核首卷角色、关系、物品和地点 | `analysis.reviewed.json` 与逐章覆盖矩阵 | 首卷完整姓名、实体类型、出处正确；不从出场频率推断身份和关系 |
| DEV-005 | 标注五卷、跨章 Arc、Beat、因果边与线程 | 五模块标注及长篇 schema 说明 | 未来规范事件不算既成历史；关键后果均有条件和来源 |
| DEV-006 | 声明世界规则、角色知识、状态变化与文风 | 规则、角色声音样本、可见性与负向约束 | 每项硬约束有来源或明确互动设计裁决；传闻与客观事实分开 |

至少明确以下数据语义：

- 原著事实、互动设计规则和分支新增事实分别标记来源；未来规范变化与当前实际状态分离。
- 每个角色分别保存已知、未知与已遗忘事实；事实真实存在不意味着所有角色都知道。
- 道具所有者、持有者和位置分开；不把掌心印记默认视为可转交物品。
- 因果线程保存触发、到期、处理条件与证据；阶段完成和全书终局分开。
- 每个入口明确位于事件之前还是之后，哪些前史已生效；不能出现开局自动完成用户尚未作出的决定。

首卷标注先选山门、废井/残印和离宗相关场景校准结构，再补齐第 1–10 章。全书候选目录保持完整，末卷待审项保留；首卷所依赖的幕后规则也必须通过审核。

## D2：编译并加载真正可用的包

**DEV-007：审核输入编译。** 在 `package_builder.py` 接收经审核的实体与长篇标注，由 Python 分配/复用稳定 ID、检查引用并生成模块。原始候选文件与最终编译输入均保留。相同输入和编译器版本应产生相同的核心内容哈希；构建时间等非确定性信息放在独立报告里。

**DEV-008：长篇模块与兼容校验。** 在 `content.py`、`package_builder.py` 和 `module_context.py` 中同步处理新字段、索引、模块审计与加载。新增 schema 版本必须有明确拒绝或兼容路径；旧包未声明长篇能力时，不自动推断其支持卷级推进、知识撤回或线程账本。

**DEV-009：首卷可用范围。** 优先全书索引加已审核内容开放范围，在建档、入口选择和后继转移处统一校验。若这会显著扩大首轮实现，则采用独立首卷派生输入与独立包 ID，记录父母本哈希及范围；D1 结束时确定方案。两种方案都要明确显示“切片完成”，不得拿第十章当全书终局。

验收包含：合法包可加载；源哈希不符、未审核执行字段、悬空引用、模块篡改、未来入口或越过开放边界均失败；旧包回归通过。同版本重新构建不能覆盖现有包，升级用新版本。

## D3：让选择正确改变本局状态

**DEV-010：上下文按当前事实装配。** 扩展 `ModuleContextResolver.resolve` 的相关实体与可见性选择。按当前角色、位置、物品、行动目标和未结因果选取信息；不能只依赖最近 N 条账本。全书秘密留在后台，正文模型拿到当前必要的约束投影。

**DEV-011：受控状态变化。** 复用 `branch_ledger.py`、`cocreation.py` 的规则校验与状态补丁，按契约支持交付、受伤、能力阶段、得知/遗忘、关系与线程变化。只有现有表示不足时才扩展账本类型；状态校验是核心规则的责任，不能只检查账本条目是否为合法 JSON。

**DEV-012：持续性与预算。** 验证新入口状态构造、分支继承、恢复、事件重放、请求幂等和事务一致性。固定规则与风格目标小于 1,000 tokens；其余预算按实际模型计数与实测设置。记录模块路径、有效事实 ID、输入规模和模型调用次数，超预算不能静默删掉关键规则。

主要文件：`module_context.py`、`branch_ledger.py`、`cocreation.py`、`entrypoints.py`，必要时涉及 `storage.py`。仅调整共创路径所需的持久化；读取服务仍不得初始化或迁移数据库，测试使用临时库。

通过线：同一物品不会重复占有；角色获得秘密前不会说出它，失去相关记忆后不再直接引用；换章不重置伤势或承诺；分叉后不同选择各自保持；未提交草稿不产生事实。

## D4：把事实正确转化为可读正文

**DEV-013：行动与剧情方案绑定。** 复用现有 Planner，把用户本次核心意图、受控结果、冲突推进和留下的下一步决定关联起来。方向选择与自由文本走相同的事实边界。允许自然的环境描写与过渡句；新增会影响后续行动的角色、道具、能力或线索必须先有受控登记。

**DEV-014：包驱动的正文检查。** 接入本书风格、人物声音、可见信息和规则。检查两层：本地确定性检查负责引用、状态和明确禁令；语义检查与人工试玩负责人物动机、行动后果及自然可读性。不用关键词出现或正文长度代替“用户意图落实”。

**DEV-015：有限修复与失败恢复。** 保留已有有效初稿与局部修复预算；新增场景验证不得绕过修复次数、源段落预算和模型调用上限。修复后再次检查，仍失败则保留原分支并返回可恢复结果。记录每次拒绝与修复的具体原因。

主要接点在 `cocreation.py`、实际 API 生成调用路径和相关测试。`api_reader_quality.py` 等未提交工作先核对责任与适用书籍；本书专用规则从包中装配，避免候车室人物或时间规则误作用于《太虚遗录》。不借此重构整个 API。

验收报告同时记录：首稿通过率、修复率、失败率、调用次数、上下文 token、正文等待时间，以及具体阅读问题。先建立基线再提出性能阈值，不提前宣布“低延迟”或文学质量达标。

## D5：先完成第一卷的可玩验收

创建本书隔离场景集，保留输入、包版本、入口前史、父分支、期望变化、禁止变化、实际状态和正文证据。场景中的互动行为属于测试设计，不自动认定为原著事件。

| 场景 | 需要证明的行为 |
| --- | --- |
| 山门开局 | 人物、处境与目标清晰；没有提前揭示父亲或残印的秘密 |
| 中段角色介入 | 开局只继承指定入口之前的历史，玩家角色不会再作为独立 NPC 行动 |
| 道具转交或被阻止 | 在审核支持的场景里，行动结果符合可携带性、持有关系和在场条件；后续不出现物品复制 |
| 记忆代价 | 仅在已审核触发条件满足时发生，后续认知与具体失去的记忆相符 |
| 持续偏离 | 至少三个连续回合承接用户改写，不无理由拼回原著 |
| 长程因果 | 插入足够多的其他事件后，较早的伤势、承诺或持有关系仍影响当前回合 |
| Arc 完成与续读 | 当前冲突产生阶段结果，未结事项明确转交下一阶段，首卷末尾不冒充终局 |
| 分叉与故障 | 两个分支互不污染；恢复、超时、无效输出与重复请求不导致半完成状态 |

每个场景先跑确定性验证，再进行必要的真实模型抽样。至少一个完整 Arc 和一个连续偏离路径保留完整正文证据；不是只展示三段挑选过的成功文本。

人工阅读检查采用四项明确判断：读者能否说清发生了什么和为什么；人物行为能否对应其动机与知识；用户意图是否产生后果或明确阻碍；段落是否自然承接并把下一次决定留给用户。每个问题引用具体回合和原句，不只打“文笔不错”的总分。

## D6：扩展到五卷与全书终局

依次交付第 11–20、21–30、31–40、41–50 章，每卷复用 D1–D5 的标注、编译与验收流程。每次扩展同时检查前卷角色状态、记忆代价、物品流转、未结线程和各势力关系。

第 41–44 章旧线需先给出原文对照和冲突清单。能够凭证据澄清的直接记录；必须改变原著含义的修文形成明确修订稿后再进入内容变更流程，不能在故事包中隐瞒原著矛盾。

全书验收至少包括所有规范边与重要条件边的自动检查、每卷关键场景、四次跨卷承接、持续偏离与全书终局的真实模型抽样，并说明没有覆盖的路径。终局检查关键目标与线程的具体处理证据，不由模型一段总结自行宣布完成。

候选发布交付：全书版本化包、源与审核清单、根包和模块审计、覆盖矩阵、场景数据与运行报告、人工试玩意见、已知限制、旧会话继续绑定旧版的验证。通过内容和技术验收后再决定正式安装/发布，不覆盖旧包与已有用户分支。

## 检查策略与完成定义
