## 目的

`python3 -m open_story_engine evaluate-live` 用固定场景验证共创链路的运行时边界。它不是默认测试，也不替代 Python 自动回归、StoryPackage 校验或玩家 CLI 的 SSE 人工阅读验收。

评估加载由 `STORY_PACKAGE_ID` 与 `STORY_PACKAGE_VERSION` 选定的固定 StoryPackage，并为每个场景新建内存 SQLite 会话；不会写入 `STORY_DATABASE_PATH` 指向的项目数据库。评估报告不包含模型原文、请求正文或密钥。脚本生成的模块包通过 `load_runtime_story_package(..., lazy=True)` 加载：只读根总清单，正文 Planner 只按当前章节、当前剧情节点和已选角色解析所需模块，绝不读取 `reader/` 原著章节模块。

为将剧情行为验收和中转站 SSE 波动分离，`evaluate-live` 忽略 `STORY_LLM_STREAM` 与 `STORY_LLM_TIMEOUT_SECONDS`，固定使用普通 JSON、单请求 60 秒、禁用 JSON/SSE 传输降级。玩家 CLI 的 SSE 优先与 JSON 回退逻辑不受影响，应单独人工验收。

## 命令

先在 `.env` 或当前 shell 设置 `STORY_LLM_BASE_URL`、`STORY_LLM_API_KEY`、`STORY_LLM_MODEL`，然后执行：

```bash
STORY_PLANNER=openai \
STORY_LIVE_EVALUATION=1 \
STORY_LIVE_EVALUATION_MAX_CALLS=12 \
STORY_PACKAGE_ID=rainy-waiting-room-source \
STORY_PACKAGE_VERSION=0.1.16 \
python3 -m open_story_engine evaluate-live \
  --output /private/tmp/open-story-engine-python-live.json
```

`STORY_LIVE_EVALUATION_MAX_CALLS` 默认是 `8`，可设为 `1` 至 `20`。报告只把带有 transport 记录的 HTTP 请求计入调用次数；本地归一化、状态拒绝和审计记录不计为模型调用。固定 JSON 验收会在下一次生成、续写、修复或事实核对请求发出前检查预算；场景内耗尽预算会失败，后续需要模型的场景标为 `not_run`，离线场景仍会执行。

启用两轮事实核对的模块包，六场景中的三个生成章节至少需要 9 次请求。因此上面的完整验收示例显式设为 12；默认预算不会被运行时自动提高。短稿补足、格式重核和局部修订仍可能耗尽这一预算。

传入 `--scenario <场景 ID>` 时只运行该场景：

```bash
STORY_PLANNER=openai \
STORY_LIVE_EVALUATION=1 \
python3 -m open_story_engine evaluate-live \
  --scenario locked_signal_room_state \
  --output /private/tmp/open-story-engine-locked-room.json
```

指定 `--output` 后，命令会先写入 `runStatus: "incomplete"`，并在每个场景完成后更新报告。中断时已完成场景会被保留，不能视为完整验收结论。

## 场景

历史单文件包保留原有固定场景。对于 `metadata.authoringSource: source_text_script` 的模块包，脚本改用以下六场景；两类包不会混用节点 ID 或断言。

| 场景 | 是否调用真实模型 | 通过标准 |
| --- | --- | --- |
| `modular_catalogs_are_lazy` | 否 | 进入菜单后只装载已定位剧情节点，而非全量节点索引。 |
| `source_character_entry` | 否 | 原著角色入口绑定当前阅读章节与连续性关系。 |
| `new_character_entry` | 否 | 新角色入口独立分叉，仍处于原故事状态范围。 |
| `module_context_current_chapter` | 是 | Planner 审计记录当前章节模块上下文，且模块路径不包含 `reader/`。 |
| `chapter_switch_state_continuity` | 是 | 两个连续章节标题不同，`sourceProgress` 和分支账本连续推进，玩家位置与角色位置表一致。 |
| `request_idempotency` | 否 | 相同 `requestId` 不重复生成或追加分支。 |

真实模型场景可能因短稿续写而发起额外 JSON 请求；这些请求同样计入上限。评估不会为了凑足调用数而重复生成。

模块化 Planner 还会把生成正文连同当前受控模块和状态发至同一端点进行事实核对，`generationStage` 为 `fact_review`；修复后的核对为 `semantic_repair_fact_review`，请求同样计入预算。核对只影响草稿是否可用，不修改权威状态；具体事实问题最多修复一次，不因文风偏好自动重写。

`python-v0.23` 在上述核对及本地守卫通过后，增加单独的 `fact_support_review` 请求。它检查同一句中每个事实的主体、行为、时间、条件和结果，接收完整候选正文、候选引用及同一批有界证据，不接收初审的通过结论或理由。无引用段落同样须覆盖；不增加模块或原著读取。发现问题沿用现有局部修订及整章一次纠错上限，修订后再次复核，阶段记为 `semantic_repair_fact_support_review`。漏检段落、无效问题定位或传输失败直接拒绝，不为此新增重试。每个到达此阶段的候选稿增加一次请求，计入总预算。独立请求仍使用同一模型，不代表独立事实来源或完整语义证明。

`python-v0.25` 的独立复核返回覆盖全部段落的 `checks`，逐段明确 `status: allowed | conflict`。允许条目只给编号与状态；冲突条目提供最小错误引文、理由和局部修订。同一段不得重复，通过条目不能同时携带错误引文或修订。这样避免把判为“允许创作”的说明塞入问题数组而被误拒。旧的 `checkedParagraphIds + conflicts` 仅保留校验兼容，两种格式不能混用；脚本不会通过扫描理由中的“允许”等词自动撤销冲突。

事实核对通过 `checks` 覆盖每个编号段落。`python-v0.24` 将当前正文与已装载证据拆成带不透明 `ref` 的原句 `spans`；每句保留原文，结构化证据保留字段 `path`，不混合不同人物或字段。引用由脚本根据所属段落或证据、句子位置、字段路径和原文生成。`supported` 返回 `supports: [{claimRef, evidenceRef}]`，模型只复制输入中的完整标识，不自行数句子。脚本在当前段落和证据中精确查找，拒绝不存在、跨段、过期或混用旧字段的引用，不尝试猜测其目标。多个事实或多条依据分别列出对应关系。定位正确只证明引用存在，语义支持仍须复核；设备规则继续执行下述本地检查。

旧的 `supports: [{claimId, evidenceId, evidenceSpanId}]` 和 `supports: [{claim, evidenceId, evidenceQuote}]` 保留严格校验兼容，仍要求编号或引文实际存在；当前提示只要求 `ref` 格式。`non_factual` 用于不新增持久事实的普通动作或提问。`conflict` 仍用 `quotes` 数组列出最小错误断言，并提供问题理由和完整修订段落 `correctedText`，避免把含正确事实的整句全部强制删除。旧格式的整段 `quote` 须先重核定位；运行时只允许标点、引号和对白插语的可证明归一化，不忽略否定词、变换文字顺序或跨段匹配。

`python-v0.26` 的初审不再要求模型重复列出 `evidenceIds` 或无问题条目的理由。`supported` 只返回段落编号、状态及引用，`non_factual` 只返回编号和状态；脚本从 `evidenceRef` 推导去重后的证据清单，再执行原有完整引用与事实校验，不把推导出的清单当作事实通过证明。冲突条目仍必须提供理由与可定位的问题。旧响应显式提供的字段仍需验证，不覆盖无效值。没有完整最终 JSON 的初审可使用既有的一次格式重核机会，不回填截断输出、不重写正文，也不增加传输重试。

身份依据 `characterIdentityEvidence` 由解析脚本从已加载角色证据和节点材料中提取，只使用当前来源进度以内明确出现姓名的身份揭示句。若节点摘要截掉了同段末尾的揭示句，保留来源行范围完全相同的描述与揭示句为两个独立片段，不伪造拼接原句、不从相邻段落猜测别名、不加载全文。这些依据同时进入生成与两轮复核，要求同一人的外貌称呼、职务与姓名保持一致；此提示不代表完整的角色指代证明。

`requiredHistoryClaims` 对“你让我签的时候”等明确过去行为增加窄范围检查：候选不能归为 `non_factual`，支持引文必须覆盖该行为原句，不能用相邻的“泵坏了只是小事”替代过去要求签字的依据。带问号的句子仍须核对这类往事前提；明确未定假设不进入此检查。此保守边界可能要求改用来源措辞，且不穷尽所有往事表达；普通事实的语义支持仍依赖复核。

`python-v0.27` 增加 `sourceDialogueContext`：脚本按已有来源段落编号，为代词对白保留紧邻前后段落，每段标记 `prior | current`，编号不连续时不拼接。只使用已加载的有界材料，不补读全文。若紧邻上一段的末句以一个已登记人物及可识别的动作谓语开头、没有其他登记人物或对白，且当前对白之前没有更换人物的叙述，脚本可按这一窄语法模式给出 `speakerName` 和原句 `speakerBasis`；所有格、多人同句、引号内姓名和断开的段落不用于这种标注。动作模式包括后退、站起、抬眼等有限表达，不把任意姓名前缀当成主语。这是有来源的有限指代解析，不是任意对白的完整语义证明，也不修改状态。

“你刚才说的”等代词来源声明由脚本定位为 `requiredAttributionClaims`。初审若判为 `supported`，须另给 `sourceAttributions`，明确正文声称的来源 `claimedSource`、证据中的说话人 `sourceSpeaker` 及引用。脚本验证候选覆盖、姓名在相邻正文及所引证据中可定位、引用有效且两个来源姓名一致；仅引用话语内容、来源不一致或将声明归为 `non_factual` 均不能通过。格式重核保留候选的相邻正文。明确署名的普通复述仍走常规事实核对，避免把复述者与原说话人不同当成错误。模型仍可能错误解析姓名，不能把字段一致等同于完整事实证明。

短稿补足不再接收额外原著证据，仅接收现有正文、原结尾和所需篇幅，任务限定为当下感官与情绪，不新增对白、线索、过去动机或关键动作。脚本精确提取实际插入的 `expansionAddedText` 交给两轮复核，全文仍执行相同状态与事实校验。原句、结尾和其他段落继续由脚本保留，不因补足自动改写。

跨章承接仍限定最近两个节点、每个最多 1,200 字，但改为保留末尾完整自然段，避免从半句对白开始；相同正文的宏观方向节点去重。单个末段超过限额时不截取残句，因此可能没有该节点的正文摘录；分支账本与权威状态仍保留，不能据此编造缺失前史。

设备或通信与“只允许、共用、都走”等限制表述同时出现时，脚本提取为 `requiredRuleClaims`。这些候选不能归为 `non_factual`，也不能只引用同段环境描写后通过；支持记录必须覆盖对应规则句。对这类规则采用保守边界：归一化后的规则原句还必须连续存在于所引用的证据原句，不能以“放行期限”的真实引文证明新编的“通信线路占用期限”。无法建立该对应时要求重核为冲突并修订。代价是这类规则的自由转述可能被要求改用素材原句；普通事实转述不受此逐字规则限制。明确的疑问和未定假设不进入这一窄范围检查。此检查不穷尽所有规则表达，也不能证明完整语义蕴含或排除全部漏检。

时间条件与限制跨逗号相连时也作为完整候选保留，例如“信号恢复之前，谁都不能进设备间”；“设备间进水、里面危险”的依据不能支持新增的信号恢复条件。已通过场景中的实际漏检样本已验证会被这一规则拒绝；明确疑问和未定假设仍保留原有边界。

每次核对最多进行一次格式修正。只重核格式有误或缺失的段落，输入包含这些段落、已有错误记录与理由；合并后按编号恢复完整核对结果，不能覆盖其他段落，也不能撤销已有 `conflict` 或省略其原理由。只有编号重复、越界或无法映射时才请求完整核对记录，不重新生成正文。仅凭问号不会自动降级为 `non_factual`，疑问中的事实前提仍需核对。错误引文夹带素材已有且修订稿仍保留的独立片段时，先要求精确定位，不强迫编辑器删除正确事实。对白中明确的说话人插语可在定位时忽略，但否定词、文字顺序与实际事件描述不可忽略。请求计入预算，审计阶段为 `fact_review_format_repair`（正文修复后带 `semantic_repair_` 前缀）；传输失败不触发此重试。

事实支持的引文先做仅标点归一化的定位，再尝试对白插语归一化，避免正文中的插语被去掉而摘录末尾的同一插语仍保留，造成不对称误拒。错误片段数组兼容 `quote` 字段别名，仍执行同样的非空、逐项定位和修订校验；旧的整段字符串 `quote` 不因这一兼容而直接通过。

格式重核保留原段落及原句引用，不为子集重新生成标识；规则候选同步限定到待重核段落。旧编号格式的越界错误仍返回错误的 `claimId`、`evidenceSpanId` 及可选编号；新格式要求直接复制当前 `spans` 的完整 `ref`。运行时不把错误引用猜测映射到其他句子。

核对结果提供完整局部修正时，运行时直接按段落编号应用建议，再执行全部守卫和一次新的事实核对，不另外发起编辑请求。缺少可用修正时，才请求局部 `replacements`。两种路径都要求编号有效且唯一、段落确实改变，最多修改 8 段，原段落总长度不超过正文的一半（短稿允许 200 字）；其他段落保持原样。整章仅允许一次事实纠错，失败不会展示为可确认草稿。

事实核对已明确指出超过 8 个问题段落时，脚本在请求编辑前停止，不消耗一次必然超限的修订调用；不通过漏修某些段落或扩大上限来继续。此检查是在下述 `python-v0.27` 完整运行暴露问题后加入的，已使用该轮真实的 9 段冲突记录离线重放，编辑请求数为 0，未再发起真实整套验收。

修订请求前也检查问题段落的原文总长度，复用应用修订时的同一计算：超过 `max(200, len(narrative) // 2)` 即停止。完整建议和需要编辑的路径均执行；恰好处于上限仍允许修订。这项优化仅省去确定超限的调用，不改变初稿提示、事实标准或传输配置；已通过离线零调用及边界回归，不代表真实模型生成质量通过。

部分建议通过本地检查时保留这些建议，只把尚未修好的段落交给独立编辑。编辑输入用 `⟦REPAIR_GAP_n⟧` 替代含错误断言的整句，仅保留问题理由及相邻段落作衔接参考，不携带原错误引文让模型猜回原句。原稿在验证前不变；编辑结果不得含占位标记。合并修订仍受同一总段数、改动篇幅和事实核对约束，不能分别计算上限。若编辑段以至少 60 字的相邻完整段落逐字开头，只去掉这一可证明的重复前缀，原相邻段落保持不变；仅重复相邻段落而无修订内容的响应拒绝。

局部修订和随后的篇幅补足都不能在原问题段保留已标记的错误断言，也不能在其他位置增加其出现次数；无效建议不直接应用，独立编辑请求也不能绕过此检查。这样可以删除后文重复发生的动作，同时保留此前已有效发生的同一动作。修订后的模型核对会同时看到首次问题，逐项确认是否消除。这能拦截保留原句的局部漏改，不等同于证明同义改写已无语义错误，仍需完整事实核对。

本地语义守卫与模型事实核对先汇总问题，再启动一次修复。短稿若已触发本地事实错误，也先纠错再补足篇幅，避免沿着错误前提扩写。模块包的篇幅补足返回 `expansion: {paragraphId, text}`，其中 `text` 仅包含新增内容，由脚本插入最后一个自然段的末句之前，不要求模型复制原文。该段原句、顺序、结尾及其他段落的分隔全部由脚本保留。补足只能添加感官、情绪和未定思考，不能重演前文动作或对白。如果响应尾部逐字重复原末句且该句至少 12 字，脚本只去掉这一尾句，记录 `removed_expansion_ending_echo`；没有新增内容仍拒绝。较短结尾或其他至少 40 字的原长句重复仍拒绝；回忆旧语音不因引文相同而一律拒绝。模型核对接收合并后的完整正文及扩写段号，检查事件重复。去重后重新验证篇幅、状态和事实，阶段为 `expansion` 或 `semantic_repair_expansion`。非模块包保留原有续写路径。

事实核对区分持久事实与合法的创作性描写：通信内容、往事、设备规则、物品归属、关键行动结果须有依据；普通抬眼、裹衣服、情绪、比喻和不预设新事实的疑问不因素材没有逐字记载而拒绝。对白中的往事断言仍须核对，不因属于对白而豁免。

初审与独立复核共用同一事实边界说明。已确认电话未接通时，屏幕显示红色“未接通”等只是同一失败结果的表现，不需另有界面颜色或位置的素材；若改成收到回复、得知对方位置、断言故障原因或恢复条件，仍须依据。已确认通话成功却写此次未接通也仍是矛盾。这是模型审查口径，不是本地正则豁免，不能绕过状态守卫或以相同词语自动放行。

素材已记录的角色发言，可以按同一发言来源引用或转述，不要求另找该角色确实说过此话的证明。例如姜序转述“陈砚说泵坏了只是小事”有来源，不代表运行时认可“泵没有危险”这一客观结论。独立复核的输入先列依据、再列正文，保留人物归属和状态优先级。

核对与生成共用 `ModuleContextResolver` 已产生的有界 `continuityText`，作为 `confirmedBranchContext` 证据。这样跨章引用已确认前文不会因为核对只拿到当前场景而被误判。该项不增加模块读取，不装载 `reader/` 或全量历史；账本与当前权威状态仍决定有效状态，正文承接不能覆盖状态。

解析器利用已有模块的来源行号，以父节点已确认的来源终点分开 `narrativeBrief`（本章新增材料）与 `priorNarrativeBrief`（已发生前史）。两者合计仍受原场景材料上限约束；前史可供记忆和因果核对，不能重新演成相识、发现或取得物品。没有父状态的旧调用保留原有上下文行为。修订复核只附原问题理由和变更段号，不再携带旧错误引文或被替换的正文；唯一核对对象是当前完整正文，并检查相邻问答是否仍依赖已删除的信息。

本地通信检查不会把明确的新说话人引入的对白归给此前提及的语音；直接引述语音的内容仍须匹配登记原句。交通检查区分明确的计划或对白请求与已完成发车，同篇后续出现实际发车时仍拒绝，不能因前面出现过请求而跳过整篇检查。

对大段循环输出，本地只在能够逐字证明全部尾部都在重复时保留首份内容，并记录 `removed_repeated_tail`。恢复后仍须通过篇幅、状态和事实核对；不足篇幅执行一次补足。有独立新结尾或不能证明是尾部循环的正文直接拒绝，不静默删改。JSON 解析只接受响应末尾完整的对象，不把推理或说明中的示例对象当成最终结果；未闭合的推理块直接拒绝。

## 判定边界

全部场景通过且实际调用数未超过上限时，结论只代表本次调用通过了场景中明确实现的断言与本地守卫。任一场景失败或未运行则本次验收不通过。它不证明整篇正文的全部因果、对白陈述、设备规则或人物往事均与母本一致；正则守卫不是完整的语义矛盾检测器。

它不证明玩家 SSE 的逐段展示、读者偏好、长期节奏或发布级文学质量。SSE 人工阅读验收与 2,000 字正文质量检查应使用隔离的试玩数据库单独执行。

发现具体内容矛盾时，即使六场景全部通过，也不能据此宣布完整生成与状态写入链路可交付。2026-09-09 已确认允许成熟的读取 API 与 HTTP 契约并行开发（本轮不编写前端页面），见[分批实施边界](api-web-architecture-v0.1.md)；这不构成生成质量验收通过。
